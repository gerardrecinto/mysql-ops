Replication

One primary, two replicas, GTID auto-position. No binlog file names anywhere.

ScenarioWhat the test does
LagStops the replica SQL thread, writes 20 rows, reads the GTID gap, restarts, waits for the gap to clear.
Stalled replicaWrites a row directly on a replica so the next insert fails with 1062, finds the error in SHOW REPLICA STATUS, removes the drift, resumes.
FailoverStops the primary, promotes a replica, repoints the other with SOURCE_AUTO_POSITION=1, proves no transaction was lost.

Group Replication

Three nodes, single primary. The test stops the primary and watches the group recover.

Tuning

Find the slow query, read the plan, change one thing, measure again.

# the digest view shows rows examined vs rows sent
SELECT DIGEST_TEXT, SUM_ROWS_EXAMINED, SUM_ROWS_SENT
FROM performance_schema.events_statements_summary_by_digest
ORDER BY SUM_ROWS_EXAMINED DESC LIMIT 1;

Docker and Kubernetes

A 70-line service reports replica health. It is built, scanned, deployed to a kind cluster in CI, and checked from both sides.

Healthy replica

HTTP 200

Both threads running, lag under the limit.

Stopped SQL thread

HTTP 503

With the reason in the body, so a probe or alert can use it.

Image

Non-root, scanned

Trivy fails the build on fixable high or critical findings.

Jenkinsfile

Test, build, scan, deploy

Undoes the rollout on failure. Not run on a Jenkins server.

What this does not prove

So you do not have to guess.

One host

Group Replication runs as three containers on one machine. Network partitions and slow disks are not tested.

Small data

300,000 synthetic rows. Plans on large production tables will differ.

Not on Jenkins

The Jenkinsfile has not run on a Jenkins server. The same steps run in GitHub Actions.
